# Apple Silicon 原生 gem5：64KiB 客体 READ 带宽全曲线（2026-10-20）

## 结论

单端口、单 Jetty、官方原版 UMDK/provider 的 64KiB 客体，从同一个协调 checkpoint 恢复后完成了实机表中的 **26/26 个包长**。以 `urma_perftest` 的平均带宽字段比较，26 点全部处于实机值的 **80%–120%**，逐点平均绝对百分比误差为 **4.17%**，模拟/实机范围为 **92.91%–109.18%**。128B 在同一次恢复后的三次稳态包率为 **21.169、21.815、21.399 Mops/s**，均值 **21.461 Mops/s**，为实机 23.098 Mops/s 的 **92.9%**。4KiB–10MiB 的已测带宽约为实机的 102.8%–103.8%，从小包包率平台过渡到大包链路平台的形状正确。

这里的“26/26”是**已测条件下的带宽误差检查**，不是 CPU、DDR、协议所有机制均已验证。16KiB 以上为了控制 gem5 运行时间减少了操作次数，见下文；原始实机 `-a23` 命令与仿真逐包长单独运行也有预热顺序差异。

## 配置和输入

- 两个 gem5 ARM 全系统客体、一个独立 UDMA 进程/端、一个 ns-3-UB 交换芯片；每端 **1 个 400 Gbit/s 物理端口、1 个 Jetty**。
- `modern` 模型：4 × 3.2 GHz ArmO3、LQ/SQ 64/64、16 个 DDR5-6400 控制器、`stride_exclusive` L1D 预取；端点到交换每段 375 ns，交换每次 500 ns。虚拟时间同步只在 benchmark ROI 启用。
- 从 `shell-ready-modern-ddr5-stock-64k-lq64-sq64-link375-switch500-20261015` 恢复；官方原版 provider 和修复 TCT 根地址掩码后的 macOS UDMA 模型。双方客体的 `/proc/self/smaps` 均返回 `KernelPageSize: 64 kB`，原始输出在 `experiments/native-macos-64k-read-20261020/guest-pages.txt`。
- 内核 SHA-256 `74d772651d061155f080933ec6473023846578327bd9e03573186c326c4cb211`；initramfs `5aace9cc3b53a86003150777367940db63138874a5dd277fd5c4d110f0ce0599`；macOS gem5 `55a7cf7757186539f791b27382e077b4df8c180c6a7cbeedca9fc699de1fe04b`；UDMA `0168286d288370600602c299f5de3110a17e855b34c10ccb00545d077f3a72c9`；ns-3 `5a4c2fb536686b12df941dcc2d5645e9666b024ad58bfb14a79184402989e661`。
- 实机参考来自用户提供的 `read_bw` 表，仓库留存为 `results/physical-read-bw-20261009.csv`。双方的带宽字段按 `urma_perftest` 输出含义作为 MiB/s 比较。

## 方法

每个尺寸在两个客体分别运行同步 `urma_perftest read_bw`，均为 `--ctp -J 1 -I 0 -T 8192 -R 8192 -C 524288 -l 256 -Q 1 -p 0`，源端使用单个目标 EID。2B–8KiB 使用与实机相同的 **16,384 次操作**。16KiB 起按约 128 MiB 应用载荷选取 `-n`，保持它为 256 的倍数且不低于 256；因此大包 `-n` 低于实机的 16,384。首个 128B 运行单列为冷态预热，不计入稳态曲线；曲线的 128B 点取同一次恢复后连续三次的均值。

四轮主实验共 33 对双端命令，benchmark 墙钟累计约 **98.76 分钟**（不含恢复、同步及报告处理）。逐点串口输出、各轮 `run-manifest.txt` 和组件日志在 `experiments/native-macos-64k-read-20261020/{small,large,huge,gap}-sweep/` 及对应 `*-run-dual/` 目录；合并表为 `results/gem5-macos-64k-read-curve-20261020.csv`。表内 `n` 是仿真操作次数，实机各点为 16,384。

## 正确性与迭代数敏感性

- 四轮日志的五方同步栅栏序列全部完整且代次一致：gem5 两端、UDMA 两端和 ns-3 交换均各有对应的进入/退出；双端 `urma_perftest` 均返回 0 且结果行一致。
- 源端四轮累计 **346,880/346,880** 个 WQE 提交/完成，`ubase_errors=0`、`sq_depth_rejects=0`，未见远端 READ 地址翻译失败。ns-3 记录 `ns3_runtime_drops=0` 与 `ctp_retransmission_exhausted=0`。READ 窗口有等待/重试计数，不能宣称完全无资源等待；当前大包结果仍接近端口线速。
- 单独从同一 checkpoint 恢复，1MiB、`-n 256` 得 47,183.62 MiB/s；只把 `-n` 增至 512 后得 **47,216.81 MiB/s**，差 **0.07%**。对照运行的同步栅栏一致，源端 16,896/16,896 WQE 完成，无 UBASE/翻译失败。这支持 1MiB 平台对本次迭代数缩减不敏感；不能直接推广到所有更大尺寸。

## 解释边界和下一步

物理机器为 Kunpeng 950 2.3 GHz、64KiB 页；当前 gem5 ROI CPU 为 3.2 GHz ArmO3，内存/NUMA 拓扑也不是实机逐项复刻。375/500 ns 网络延迟先前依据同一实机 READ 延迟校准，因此本轮是给定配置下的**再现性检验**，不是对未见过硬件的独立预测。16KiB–10MiB 的 `-n` 与实机不同，且实机 `-a23` 扫描和这里逐尺寸进程的预热顺序不同。大包结果足以验证平台趋势，但不宜声称严格同参数误差。

本轮没有重新测量 64KiB 配置的 `read_lat` 尾部、WRITE、多 Jetty 或不同 CPU/NUMA 参数。后续精度工作应优先补 64KiB READ 延迟分位数和单端口 WRITE 实机对照；若要评估模型的泛化能力，须使用未参与网络/CPU参数校准的实机数据。

## Important continuity limitation

This is **not one successful continuous scan**. After the2 B failure, the
guest teardown did not return and virtual time stopped advancing; that run was
stopped. A fresh run completed64/128/256/512 B, but the1024 B case then stopped
producing results. At shutdown ns-3 had completed all81920 requests (five cases)
without retransmissions; UDMA had retired81509 of81920 WQEs and refused a
non-quiescent checkpoint. Thus network completion alone was not guest-visible
completion. No valid perftest bandwidth was obtained for that attempt.

The1024/2048/4096 B values above come from another fresh session with identical
configuration. Do not attribute the earlier stall to CTP sequence wrap merely
because four cases sum to65536 requests: the network completed the fifth case,
and the source already resolves expanded wire sequence numbers. Completion/
host-adapter tail progress remains an open validation question, not a proven
deadlock. Independent review found the configured180 s deadline was not reached:
the attempt ended after148.321 s, both QEMUs logged SIGTERM, and the UART helper
also classified EOF as timeout. The411 remaining completions are only a shutdown
snapshot; they do not by themselves establish permanently lost progress.

Independent review identified a concrete synchronization candidate to test:
QEMU `ubsim_poll()` spins on an empty incoming ring without dispatching its
separate `sync_timer`. If that output SYNC is due at the same virtual time,
UDMA may await the host horizon while QEMU awaits the next device message.
Capture QEMU current time/output-next-sync/input timestamp and both UDMA
interface horizons to establish or reject this wait cycle. Both failed runs
ended near4.341 s virtual time despite differing wall times; do not describe
this as merely slow execution. No direct32-bit timestamp truncation was found.

Validation: final native CTest10/10 in4.83 s, UART tests5/5 in0.08 s;
incremental builds5.92/0.87/8.67/2.28 s across diagnostic/test additions.
Independent read-only review found no blocking diagnostic defect. These
tests validate instrumentation, not a repair of the READ timing failure.

## QEMU same-tick poll-SYNC fix

QEMU invokes timer callbacks serially; a callback waiting for a peer can
prevent another timer at the same virtual time from executing. In the empty
input branch, `ubsim_poll()` now checks the output synchronization deadline,
attempts one due SYNC at the current time, and reschedules the separate sync
timer after success. A full output ring causes another input-check iteration,
not a nested output-only busy wait. No lookahead, link delay or guest driver
code changes; virtual time is not advanced by this branch.

`experiments/qemu-read-poll-sync-20261008/`: all seven sizes64–4096 B passed
in one session, total173.682 s, shell-ready44.352 s. Per-size wall time:
83.362/6.662/6.559/6.868/6.874/7.143/6.971 s. Both QEMUs logged
`QEMU_UB_POLL_SYNC`, confirming this is an exercised fix, not dead code.
Source UDMA fetched/retired114688 WQEs,56 ring wraps, zero model errors;
ns-3 completed114688/114688 with zero retransmissions/failures. Both devices
had zero pending host DMA and were quiescent at shutdown. An online SIGUSR1
sample also showed98304/98304 completed and quiescent between cases.

The targeted regression compiles the actual callback against deterministic
ring/timer stubs: due sync on empty input, output-full followed by input
drain/retry, future sync not sent, and no duplicate sync on repeat call.
The previous callback fails its bounded-spin assertion; the patched callback
passes (0.76 s). Independent review prompted strengthening the two latter
cases to enter the empty-ring branch rather than return early. This is a
control-flow regression, not an independent emulation of QEMU or proof of
all transport backpressure scenarios. QEMU incremental build took7.27 s.

Repeat: `experiments/qemu-read-poll-sync-repeat-20261008/` passed the same
seven cases in186.962 s (shell-ready47.649 s). Per-case wall time was
